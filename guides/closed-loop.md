# spec 与 plan：写、核、执行后对账

要治的病：每一层都写了，每一层的测试都绿，整条链却从来没跑通过一次，只是不报错。
根因是**拿自己写的计划验收自己的产出**：计划漏列的那一环（界面入口、开关的写入口、输入数据的生产方）没有任务去做，也没有测试会红；测试的输入是夹具造的，真实上游一条数据都没产出时照样是绿的。

适用：新增或改变用户能感知的能力，或新增表、列、开关、枚举值、定时任务、跨进程调用。

## 1. 写 spec：必须有「闭环链」一章

```markdown
## 闭环链
一句话闭环：用户 <做什么> 之后，在 <哪里> 看到 <什么>。
（学习/反馈类再加一句：下一次 <做什么> 时，<哪里> 与之前不同。）

| 环 | 发生什么 | 由谁触发或生产（文件::函数） | 正向可观测量 | 失败时谁看得见 |
|---|---|---|---|---|
| 1 入口 | | | | |
| 2 接口 | | | | |
| 3 落库/任务 | | | | |
| 4 消费 | | | | |
| 5 用户可见结果 | | | | |

输入清单（本功能读取、但不由本功能产生的数据）
| 输入 | 生产代码里的写入方 | 现状：已有 / 本期补 / 本期不补（需求方知情） |

实跑剧本（写给不知道实现的人）：前置 → 基线 → 第 1 步应看到… → 第 2 步…
```

- 每一次跨进程、跨语言、跨队列的交接**单独成一环**。断点绝大多数在交接上。
- 「可观测量」必须是正向的：多了一行数据、界面上出现了某个元素。「不报错」「返回 200」不算。
- 「失败时谁看得见」不许留空。填不出来说明这一环失败是静默的：要么补可见性，要么写明「静默，已知」。
- 写**生产代码**里的写入方。测试、种子脚本不算。
- 阈值和前置条件（累计 N 次、开关打开）写进链里，并说明真实使用中达不达得到。

## 2. 写 plan：逐环覆盖

- 闭环链的每一环、输入清单里每条「本期补」，都能指到 plan 里的一个任务。指不到，plan 不合格。
- **plan 的最后一个任务固定为「闭环实跑」**，不许改成「跑全量测试」。

## 3. 核 plan：追调用链，不按章节打勾

按 spec 章节打勾只能证明「有个任务提到了这件事」，证明不了「这件事真的会发生」。逐项追：

1. **每个新函数：谁调用它？** 只有测试在调用的是死链。定时任务要查注册的地方。
2. **每个新状态：怎么进入、怎么退出？** 只有进入没有退出就是死胡同。
3. **每个新字段：谁写、谁读？** 只读不写的字段恒为空，测试却全绿。
4. **端到端走一遍**：从用户点第一下到最终效果，逐环点出负责的任务名，点不出来的就是断点。
5. **并发**：两个人同时操作、定时任务和人工操作撞上会怎样？「先查再写」的幂等就是 TOCTOU。
6. **规模**：拿生产的真实数据量代进去算一遍。
7. **抢资源**：新链路会不会被已有的调度器或 worker 顺手接管？

## 4. 开工前：核对 plan 和实际代码

- plan 里「要改的文件」是写 plan 时的假设。动手前 grep 一遍，确认功能实际在那个文件里实现。不对还照字面改，是「空改」：改了，功能上什么都不会发生。
- 发现偏差，写成「plan 写 X，实际是 Y，原因 Z」，**先报告、再按实际改**，并写回 spec 和 plan。

## 5. 交付前：闭环实跑，并写回 spec

1. 从真实入口触发：浏览器里点，或带真实登录态发请求。不直接调内部函数。
2. **中间表不许造数据**，只准备用户正常就会有的起点（账号、项目）。
3. 先记基线，再做动作；断言落在最后一环，逐环记录实际值。
4. 学习/反馈类跑第二轮，证明行为确实变了。
5. 用了替身（模型、支付、外部服务）的环，标「替身实跑」。
6. **交给不了解实现的独立代理执行**，只给剧本，不给 plan 和代码位置。它走不通就是没闭环，实现方不能替它解释成「通了」。

   给走查代理的说明：
   ```
   你是第一次使用这个功能的用户，不了解它的实现。
   应用地址：<地址>　账号：<账号>
   严格按剧本操作，每一步记录：做了什么、实际看到什么、与「应看到」是否一致。
   不一致时不要绕过、不要读代码找原因，原样记录后继续；走不下去就停下说明卡在哪。
   不要直接改数据库，不要调用剧本以外的接口。
   <剧本>
   最后给出：每一步的结果表；是否走通；没走通的话卡在第几步、界面显示了什么。
   ```
7. spec 末尾写「实跑记录」：日期、commit、环境、执行者，加一张逐环状态表（已实跑 / 替身实跑 / 仅单测 / 未验证）。
8. **不是每一环都「已实跑」就不许说「完成」**，结论写「完成到第 N 环」，并列出其余各环状态。
9. 之后的修复改动了某一环，从被改的那一环重跑到最后一环。
